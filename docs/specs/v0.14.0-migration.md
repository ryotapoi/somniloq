# v0.14.0 専用移行契約

この文書は専用 `migrate` の振る舞いの正本である。現行の通常 schema 更新や `import --full` に本契約を適用しない。設定・入力 identity・通常 REF は [設定と identity の契約](v0.14.0-contract.md) に従う。

## 起動と固定 snapshot

起動形は `somniloq migrate --config NAME_OR_PATH --from PATH` とする。両フラグ必須、位置引数なし、source 選択や `--full` は設けない。移行先は設定の `db`、再取り込み元は設定の全 Codex 入力。`--from` は呼び出し時 cwd を基準とする相対 path または絶対 path、先頭 `~/` は home 展開し、symlink 解決後の実体を使う。設定の path 解決は設定契約に従う。元と先が同じ canonical path または同じ file identity の hardlink なら開始前に拒否する。

`--from` には、利用者が事前に SQLite backup 等で作成して以後変更しない standalone snapshot を渡す。稼働中の DB の更新追従は対象外。既存 `-wal` / `-journal` を伴う移行元は拒否する（空でも拒否）。`-shm` の有無だけでは内容の完全性を示さないため、存在時も拒否する。snapshot を read-only で開き、SQLite の整合性確認と形状確認を行う。schema を自動修正する通常 `OpenDB` 経路を使わない。

digest は snapshot ファイル全 bytes の SHA-256、小文字 64 桁 hex。path、mtime、DB の schema revision、論理行の hash は digest の代用にしない。読み取り前後で同じ bytes digest を確認し、変化したらコピーを確定しない。元 DB への書き込み、checkpoint、schema 更新を行わない。digest が同じなら snapshot を別 path へコピーしたものでも同じ移行元。移行先の sidecar は移行先の SQLite transaction に従う。

## 受理する旧形式

旧形状名は `legacy-v013`。`PRAGMA user_version=0` であり、ユーザー定義の table は次の3個だけ、view と trigger はなし。以下に示す旧最終形状だけを受理する。v0.2 の `project_dir`、`repo_path` 欠落、source 欠落、未知追加列、未知 source、将来 revision、既に新 schema の DB は拒否する。古い整数版なら何でも受理する方式にはしない。

列の順序・宣言 type・NOT NULL・default・PK position は以下のとおり（`-` は default なし）。PK を持つ TEXT 列でも明示 NOT NULL のない列は NOT NULL=0 である。

| table | 列順（name:type:NOT NULL:default:PK position） |
| --- | --- |
| sessions | `source:TEXT:1:-:1`, `session_id:TEXT:1:-:2`, `cwd:TEXT:0:-:0`, `repo_path:TEXT:0:-:0`, `git_branch:TEXT:0:-:0`, `custom_title:TEXT:0:-:0`, `agent_name:TEXT:0:-:0`, `version:TEXT:0:-:0`, `started_at:TEXT:0:-:0`, `ended_at:TEXT:0:-:0`, `imported_at:TEXT:1:-:0` |
| messages | `uuid:TEXT:0:-:1`, `source:TEXT:1:-:0`, `session_id:TEXT:1:-:0`, `parent_uuid:TEXT:0:-:0`, `role:TEXT:1:-:0`, `content:TEXT:1:-:0`, `timestamp:TEXT:1:-:0`, `is_sidechain:BOOLEAN:0:FALSE:0` |
| import_state | `jsonl_path:TEXT:0:-:1`, `source:TEXT:1:-:0`, `file_size:INTEGER:0:-:0`, `last_offset:INTEGER:0:-:0`, `imported_at:TEXT:1:-:0` |

全 table は通常 rowid table（WITHOUT ROWID / STRICT でない）。各 source 列は `CHECK(source <> '')`。messages は `(source,session_id)` から sessions の同列への複合 FK（更新・削除 NO ACTION）。index は各 PK の SQLite 自動 index と `messages_session_idx(source,session_id)`（非 unique、全行、昇順）だけ。他の unique 制約・CHECK・FK・index はない。空白や SQL keyword 大文字小文字の差は許すが制約の意味は同じでなければならない。`sqlite_*` 内部 object はユーザー object 数に含めない。

形状が一致しても整合性確認、FK 確認、非空 source/session ID/uuid と source=`codex|claude_code|cursor_agent` のデータ確認に失敗した snapshot は拒否する。空本文や欠落日時の空文字列は拒否しない。旧正規化値を失わず限定コピーすることが目的で、任意の壊れた DB の修復は行わない。行の text は SQL プレースホルダを使う。

## 初回コピーと再実行先

新 schema の revision は `PRAGMA user_version=1` とする。旧 agent の `sessions.version` はこの版とは無関係。初回は移行先が不存在、または transaction 開始時にユーザー object がなく revision=0 の空 DB だけを受理する。通常作成済みの新 DB を空件数だけで移行先と認めない。

一つの transaction で新 schema、旧 sessions/messages の全限定コピー、revision=1、および次の意味を持つ単一 receipt を保存する。receipt の保存先は `migration_origin`（`id INTEGER PRIMARY KEY CHECK(id=1)`、以下の各値は NOT NULL。`copy_complete INTEGER CHECK(copy_complete=1)`、他値は TEXT）。正常新 schema にもこの table を作るが通常作成では行を入れない。再実行では id=1 の一行だけを認める。値と原子性を変えない。

- `snapshot_sha256`: 上記 digest。
- `legacy_shape`: `legacy-v013`。
- `copy_complete`: true。receipt 自体が transaction と共に確定しなければ完了しない。
- `snapshot_path`: 初回の canonical path（監査用で同一性判定に使わない）。

コピーで旧 import_state の path/offset を新入力の再開位置へ転用しない。証拠照合用に旧 snapshot 側の値を読めるが、入力所属の外部キーとして扱わない。新しい取り込み状態は各 rollout を先頭から読み切った成功時に作る。

初回コピー中の失敗・中断は全 rollback。作成された空ファイルが残る場合は上記の空 DB 条件を満たすときだけ初回として再試行できる。receipt / 部分 schema が残る不完全な DB は拒否する。コピー完了後の中断は旧コピーを残し、同じ snapshot の再実行時にコピーを省いて現在の全 Codex 本人 group を再処理する。会話別の完了フラグや実行位置は保存しない。

既存移行先を再実行先として受理するには、新 revision/shape、完全な receipt、同じ snapshot digest、`legacy_shape=legacy-v013` がすべて必要。通常新 DB、receipt 欠落、不正 receipt、別 snapshot、将来版は拒否し、移行先を変更しない。新 schema revision 一致だけで再実行を認めない。

## コピー済み値と未知の表現

初回には source ごとの旧 session 行と保存済み message 行をそのまま保持する。旧 text は旧正規化済み本文一単位で、結合前の block を仮造しない。JSON `blocks=null`, `provenance=legacy_saved`。各旧会話の発言番号は元 `messages.rowid` 昇順に1から採番する。日時順に並べ替えない。旧 rowid、uuid、旧 session ID、source を移行由来の出自として保持する。

保存時刻が非空なら値を旧保存値として保持するが、実発言日時として復元できたと扱わない。由来は `legacy_saved`。空日時は未知（JSON null）。Codex の旧補完時刻を一律に実日時へ昇格させない。親、継承境界、text block、実入力など旧 DB から分からない情報は未知。旧 sidechain は旧保存値として保持し、それだけで直接親を確定しない。metadata-only の旧会話も参照可能にする。

初回の全旧会話は入力未知の legacy 会話として保持する。REF は `slq1:legacy:<snapshot_sha256>:<source>:<base64url_legacy_session_id>`。末尾は旧 session ID の UTF-8 bytes を URL-safe base64、padding なしで encode する。正常 REF の JSON array encode と混同しない。この namespace は入力不明の旧値を通常入力の同名会話と衝突させない。未知旧会話は文字列 ID、近い時刻、cwd、path 包含だけで正常会話へ吸収しない。

## UUID 出自と本人帰属を分ける

旧 Codex UUID は `codex:` + `hex(sha256(旧 absolute path + NUL + 十進の1始まり物理行番号))`。空行・無視行も物理行に含める。照合は残存 path の全行を走査して行単位で行い、先頭だけの照合を全会話の証明へ拡張しない。旧 import_state の path と現在の実体を照合対象として利用できるが、path の名前だけでは旧保存行と会話を結びつけない。移動後 path から UUID が一致しない行は未知のまま。

一致が証明するのは「この旧行を生成した物理ファイルと物理行」であり、旧 session ID が本来の本人であることではない。本人は rollout 最初の有効 metadata の ID に固定し、埋め込み親 metadata で変更しない。ordinal 境界がある行は継承文脈と本人を分離する。詳しい解釈は source の新取り込み契約に従う。

旧行の消去可否は以下で決める。

1. 一つの旧 UUID が現在の設定の一つの入力、一つの rollout、一つの行へ一意に対応すること。複数入力の証拠が競合する場合は所属未確定として旧行を残す。
2. その rollout の本人 group 全体の解析・保存が成功すること。旧行の旧 session ID が親を指していても、本人 group の継承行として識別できれば、その物理コピーを除くことができる。
3. 消去は証明できた旧行だけ。旧会話の別の未照合行を同じ session ID だけで消さない。旧会話から全行を除いた場合だけ空の旧会話を除く。metadata-only の旧会話は、本人/入力の根拠がないため残す。

全保存行が同じ入力へ一意に対応するときだけ、その旧会話の入力所属を確定できる。ただし旧 session ID を本人帰属の証拠にはしない。残行が一つでも未照合・競合なら legacy 会話全体の入力は未知。複数入力に跨る旧会話を一入力へまとめない。部分消去後の legacy REF と発言番号は初回コピー時のものを保ち、残行を再採番しない。

旧行の所属未知は置換不成功の理由となる。未解析行が0でも、旧同名会話に未照合行がある場合は `old_input_membership_unknown` を報告し、旧行を保持する。入力不明の旧コピーと、一意に読めた新入力本人の会話は別 REF で併存できる。これは旧行の置換成功とは報告しない。新規会話だけを保存した場合も retained 件数で未知を示す。

## 本人 group と置換 transaction

全 Codex 入力を走査し、`(input_id,本人 ID)` ごとに rollout を一組にする。入力を無視した同名 ID、子ファイル内の埋め込み親 ID を別の置換対象としない。同一本人の複数 rollout は canonical root からの相対 path の UTF-8 byte 辞書順、各ファイル内の物理行順で扱う。mtime、開始日時、走査順に依存させない。

本人 message に payload ID がある場合、同じ本人 group 内で同じ payload ID と同じ保存対象全文が一致したものだけを重複排除し、先の出自を代表とする。全文は保存対象 role、順序付き text block、元 timestamp を含む正規化前の対象値（ordinal の一致は重複条件にしない）。同じ ID の不一致は競合として group 全体失敗。payload ID がない行は出自が違えば同じ本文でも別発言。再実行時に前回の保存行と比較して部分追記しない。

成功 group ごとに一つの transaction で、その正常 `(input_id,本人 identity)` の前回会話を全文置換し、新親/metadata/本文/文脈/順序を保存し、証明できた legacy 行だけを除き、group 全 rollout の新 import_state を EOF へ更新する。初回コピーは既に確定済みなので他 group や他 source の旧本文を巻き込まない。新番号はcanonical本人列の位置で1から採番。前方rolloutに新本文が追記され既存本文の前へ挿入される場合は既存番号を維持せず再採番し、同じ最終ファイル集合の通常差分import・全文再処理と同じ順序/番号にする（[前方追記fixture](../../internal/ingest/testdata/v0.14.0/README.md#複数-rollout-の前方追記)）。旧の INSERT OR IGNORE 通常追記経路を置換の代用にしない。

次のいずれかで group を確定しない。既存正常会話、旧行、取り込み状態をすべて戻す。

- 読み取り・走査・解析・正規化・保存・commit の失敗。未解析行が1行でもあること（末尾の未完成 JSON も含む）。
- 最初の有効 metadata より前の user/assistant 本文、本人 ID 未確定、矛盾する本人 metadata/親・境界、境界があるのに本文 ordinal がなく文脈判定できないこと。
- 入力所属の競合、同一 payload ID の本文競合、group の一部 rollout の欠落・読み取り途中の内容変更。
- 全 rollout を読んでも本人 user/assistant 本文が0件。metadata-only によって旧本文を削除しない。

未知の正常 non-message record、空行、tool-only の正常 record は意図的無視であり未解析ではない。境界のない旧形式は文脈を推測で削らず取り込み契約に従う。親未到着だけでは失敗しない。同じ入力の親 identity を未解決の明示参照として保持し、親が後着したら接続する。入力未知の legacy 親へは接続しない。失敗した rollout の本人を特定できない場合は、その入力全体の置換を開始せず、他入力を続行する。

残存ログのない旧会話、Claude Code と Cursor Agent はコピー状態を保つ。この migrate は他 source の再解析をしない。後から Codex ログが見つかったら、同じ snapshot・移行先で再実行する。設定の入力追加も許すが、その新入力の物理証拠と既存入力が競合するなら旧行を保持する。

## 成功・失敗と出力

正常な初回コピー後は独立 group を最後まで処理し、一つの group の失敗で成功済み group を巻き戻さない。stdout は一つの JSON object、stderr は path/物理行と理由の診断（本文を含めない）。summary field は `snapshot_sha256`, `copy_performed`, `groups_replaced`, `groups_failed`, `legacy_messages_removed`, `legacy_messages_retained`, `legacy_conversations_retained`, `legacy_replacement_failures`。入力未知のため旧行を保持した会話も retained に含める。全対象 group 成功かつ所属未知による置換不成功がなければ終了0、初回コピー/再実行先拒否または対象 group/旧行の置換不成功なら終了1。ログが全くない履歴の単純保持は失敗ではない。引数・設定エラー、非対応の移行元/先 schema は終了2。I/O、snapshot/receipt 不一致、既存移行先の拒否は終了1。copy 前の拒否では stdout は空。

```text
somniloq migrate --config archive --from ./archive-snapshot.db
{"snapshot_sha256":"<64 hex>","copy_performed":true,"groups_replaced":2,"groups_failed":0,"legacy_messages_removed":5,"legacy_messages_retained":3,"legacy_conversations_retained":4,"legacy_replacement_failures":0}
```

上例は説明用 digest placeholder。旧 parent の未照合残行は、本人 parent の残存 rollout がない限りログ欠落履歴の保持であり失敗にしない。残存本人 ID と同名の旧会話に所属不明行がある場合は `legacy_replacement_failures` を増やし、group の新本文保存と別に置換不成功を診断して終了1になる。再実行で snapshot 不一致なら `migrate: snapshot digest mismatch` を stderr に出し終了1。通常新 DB なら `migrate: destination has no completed copy receipt`。本文や snapshot 全内容を出力しない。

## fixture と根拠

[合成 fixture](../../internal/ingest/testdata/v0.14.0-migration/README.md) と `expected.json` が受け入れ oracle。実ログ本文は使わない。`legacy.sql` は旧最終形状を使い、旧 UUID は架空 absolute path と物理行から計算した。初回 snapshot bytes digest は SQL source の digest でなく、fixture harness が SQLite DB を作成して閉じた時に固定する。

| 境界 | expected.json case |
| --- | --- |
| UUID 物理出自と埋め込み親誤帰属、未照合残行 | `child_physical_not_owner` |
| 同本人複数 rollout の順序・重複・競合 | `multiple_rollouts`, `rollout_payload_conflict` |
| ログ欠落・metadata-only 会話・他 source 保持 | `missing_log`, `other_sources`, `all_normal_records_ignored` |
| 入力競合・同名旧会話の所属未知 | `conflicting_input_evidence`, `unattributed_old_same_id` |
| 未解析以外の本人未確定、JSON 失敗 | `unattributed_before_metadata`, `invalid_json` |
| 初回原子性・同一/異なる snapshot・通常新 DB 拒否 | `initial_copy_interrupt`, `same_snapshot_retry`, `different_snapshot_retry`, `ordinary_new_destination` |
| exact shape の未知列拒否 | `unknown_schema` |

UUID 算式・途中 metadata による旧帰属変更・日時補完は旧 parser、旧外部キーの限界は旧 schema の実装根拠。実ログ構造の既存調査は [参考資料](../../backlog/v0.14.0-reference.md) にあり、一部分の一致を会話全体の入力所属の保証として扱わない。安全に特定できた物理行だけを消す方式を選ぶ理由は、親子混在旧行の誤消去と未知履歴の喪失を避けつつ、既知の本人全文を新 schema で利用可能にするためである。
