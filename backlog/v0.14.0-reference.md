# v0.14.0 セッションのまとまりを軸にした検索・閲覧の参考資料

対象は、複数のログ入力を一つの DB に取り込むことと、親・子・孫をまとまりとして扱う検索・原文取得。作業一覧と実施順は [backlog.md](backlog.md) を参照する。入力の識別は保存・移行・REF・検索の土台になるため、同じ v0.14.0 で移行と検索より先に実装する。

これは後続タスクの参考資料であり、現行仕様の正本ではない。第1段階で確定した契約は [v0.14.0契約](../docs/specs/v0.14.0-contract.md)、[移行契約](../docs/specs/v0.14.0-migration.md)、[追加調査とfixture](../docs/specs/v0.14.0-log-evidence.md) を正本とする。以下の合意した大枠は経緯であり、未確定と書かれた詳細も確定契約への参照で解決する。合意した方向と、実装前に具体化する契約・検証事項を記録する。実装する契約は該当する `docs/rules/`・`docs/specs/` へ反映し、実装済みの内容はこの資料から整理する。旧 CLI・JSON との互換性や旧 schema の継続利用は今回の設計条件にしない。取り込みは新規 DB と元ログを基準に検証し、保存済み履歴の移行は「既存 SQLite の扱い」に従う。

## 成立させたい利用場面

- 単語から過去の作業のまとまりを探し、選んだ会話の一致箇所と原文へ戻る。
- 指定日に実際に交わした発言を取り出し、Daily Note の材料にする。

LLM による要約は生成しない。別起動の会話を、似た文面や近い時刻だけで結びつけない。

## 複数のログ入力

設定ファイルには TOML を採用する。設定で DB の保存先と、`inputs` の一覧として表示名・source 種別・ログのルートディレクトリを指定する。たとえば標準の Claude Code と別の Claude Code の設定ホーム、Codex の別ルートを一つの DB へ取り込む。path は JSONL 一件ではなく、adapter が走査する入力ディレクトリを指す。標準の入力ルートと DB は設定生成時の既定値に使う。DB path を必須の設定項目とし、通常コマンドでは設定だけから DB を解決する。別 DB を使う場合は別の TOML を指定し、通常の `--db` override は設けない。TOML の具体的なキー・構造と CLI の綴り、現行 JSON 設定からの切り替え方法は [確定契約](../docs/specs/v0.14.0-contract.md) を参照する。

設定生成時は DB path を設定ファイルへ明記し、実行時に設定ファイル名から DB path を導出しない。`config init [NAME]` は引数なしなら `~/.somniloq/config/default.toml` を生成し、名前を指定すればその名前の TOML を生成する。既存ファイルの上書きは拒否し、作成時にも既存ファイルを置き換えない方法を使う。設定名 `foo` に対して `~/.somniloq/config/foo.toml` と `~/.somniloq/foo.db` を生成時の標準配置とし、実際の保存先も指定できるようにする。DB を操作するコマンドでは `--config` を必須とし、未指定はエラーにする。`default` は通常の設定名であり、暗黙には選ばない。設定を削除した場合も通常実行では再生成しない。未指定・ファイル欠落のエラーと CLI help に、まず `config init` で default.toml を作り、`--config default` で使う手順を案内する。別名の設定や明示 path の指定方法は補足として示す。help・version・設定生成には既存設定を要求しない。名前指定と明示的な相対・絶対 path 指定の具体的な規則、設定内の `~` の解釈は [確定契約](../docs/specs/v0.14.0-contract.md) を参照する。TOML ライブラリの選定は実装時に行う。依存ライブラリのライセンス告知は後で整理するため、今回の仕様選択からは外す。

source 種別は adapter の選択に使い、表示名は人が見分けるためだけに使い、DB へは保存しない。入力テーブルにルート path と source 種別を一度記録し、会話は短い内部 ID で入力を参照する。長い path を各発言へ繰り返し保存しない。会話の一意性は入力と source 固有の会話 identity の組で決め、Claude Code の子は共有 session ID だけで潰さない。親子関係、発言の identity、差分取り込み状態も入力をまたいで混同しない。同じ会話 ID が二つの入力にあれば別の会話として残し、入力間の本文重複を自動でまとめない。

入力 path は symlink の実体を解決し、同じ source・実体 root を同じ入力として扱う。相対 path は設定ファイルを基準に解決する方針とし、`~` の home 展開を含む具体的な正規化の手順は契約確定時に決める。ルートの移動は原則として別入力と扱い、移動済みデータを自動で付け替える一般機構は設けない。入力 path による絞り込みは本文照合・親子集約・総数計算・ページ化より先に適用する。同じ source を複数入力から取り込む場合も、REF と `show` / `search` は入力を曖昧にしない。source 種別の選択も残すが、入力 path の代わりにはならない。

## 新しい取り込み

Codex の親子関係の取り込みは必須。検索側だけでまとまりを作ろうとせず、adapter → 共通正規化型 → SQLite 保存まで関係の手がかりを通す。他 source の変更は、元ログと現行実装を比較して必要なものを確定する。

### 現行の不足と調査対象

2026-10-04 にローカルの元ログの構造と現行実装を確認した。本文は調査記録へ転載せず、必要な代表例を fixture 化する。

| 対象 | 確認できた不足・限界 | 次の対応 |
| --- | --- | --- |
| Codex | 元ログに `session_meta.payload.source.subagent.thread_spawn.parent_thread_id` があるが、[parser](../internal/ingest/codex/jsonl.go) は `source` を読まない。子 rollout に親 metadata・本文が埋め込まれる例があり、現行 adapter は metadata ごとに保存先 ID を切り替える。`subagent_history_start_ordinal` は本人の履歴開始を示す | 本人 identity と直接親を保存し、ordinal 境界がある子は継承文脈と本人の発言を分ける。親 metadata による本人 identity の上書きをやめ、差分再開時も identity・親・境界を復元する |
| Claude Code の子 | [走査](../internal/ingest/claudecode/adapter.go) は project 直下のみで、`<root-session>/subagents/*.jsonl` は未取り込み。観測した子は root と `sessionId` を共有し、別の `agentId` を持つ | 子ログを走査し、独立 identity と root 所属を保存する。再帰走査を足すだけでは現 DB の同じ session に混ざる |
| Claude Code の直接親・孫 | `parentUuid` は発言間リンクで、観測した子から別ファイルへの一致はなかった。親側 Agent call の ID、対応する tool result の ID と構造化 `agentId`、子ファイルの `agentId` をつなぐことで、子・孫の直接親を確認できた。全子でこの経路が揃うわけではない | text と別に必要な call / result metadata を保存し、厳密なリンクで直接親を復元する。直接親と root 所属を分け、本文中の agent ID だけで親を決めない |
| 原文と順序 | text は保存するが、複数 block の結合と非 text 発言の除外がある。[現行の本文取得](../internal/core/db_messages_summary.go) は sidechain を除外し、日時同値は rowid 順。Codex は発言日時欠落時に開始時刻を使う | 原文の単位と安定した発言番号を決める。子本人の本文を表示対象にし、Codex の時刻補完をやめる。Codex の継承境界は ordinal、Claude Code の通常子は呼び出し prompt からの本人イベント列を使う。根拠がない旧形式の文脈境界は推測しない |
| Cursor Agent | [観測仕様](../docs/specs/jsonl-schema.md)では日時・場所・親子が不明で、現行も補完しない | 単独の会話として保持する。根拠のない関係や日時を追加しない |

[共通正規化型](../internal/ingest/ingest.go) と [DB schema](../internal/core/db_schema.go) は会話の親・root を持たず、`sessions` の主キーは `(source, session_id)`。独立した子を識別する形式が先に必要になる。本文・順序に追加変更が必要な source は最初の調査で確定し、Codex / Claude Code の実装タスクへ含める。Cursor Agent などに独立して大きい変更が必要なら、新しい出力より前に取り込みタスクを追加する。

### 保存したい情報

| 情報 | 必要な意味 |
| --- | --- |
| 会話の識別 | 入力内で親・子・孫を独立して参照できる identity。共通の session ID だけで別の子を潰さず、別入力の同名 ID も混ぜない |
| 関係 | 同じ入力内の直接の親と所属 root、それぞれを示す根拠。直接親が未知でも分かる root 所属は残し、親が未取り込みでも手がかりを失わない |
| 原文 | 人と AI の発言本文。引き継いだ文脈と本人の発言を区別できる根拠がある場合は保持する |
| 順序 | 会話内の元の順番と再取り込みで安定する発言の識別。日時不明でも本文と順序を失わない |
| 日時 | 元ログで分かる発言日時と活動範囲。最後の記録を完了時刻とは扱わない |
| メタデータ | project、source、入力の識別、取り込み日時、および関係復元・原文選択に実際に必要な情報 |

元 JSONL 全体や tool の全文を一律に保存することは前提にしない。親子復元に必要な非本文レコードも、text 抽出とは別に読み取る。日時・場所・親が分からない場合は未知のまま保持し、ファイル更新時刻や本文から補完しない。

親の欠落、子を先に取り込んだ後の親の到着、孫、差分取り込み、同一ログの再処理、引き継いだ文脈の重複を代表例で確認する。根拠のない親を仮造せず、関係が不明な会話も単独で参照できるようにする。

## 既存 SQLite の扱い

基本方針は、**専用 `migrate` で既知の旧 DB を別の新 schema DB へ移し、元ログが残る Codex セッションだけ再取り込みして旧データを置換し、ログがない履歴は残す**こと。Claude Code と Cursor Agent の保存済み履歴もこの置換では削除しない。旧 DB を保管し、新しい移行先で部分置換を検証する。具体的な identity の変換・保持条件は [移行契約](../docs/specs/v0.14.0-migration.md) を参照する。

残存ログは同じ入力に所属するその ID の最新の正本として扱う。入力と ID が一致する既存の会話は全文を置き換える。旧 DB の行がどの入力に属したか信頼できる根拠で確認できない場合は未知のまま保持し、同じ ID だけを理由に置き換えない。再開時も同じ処理を繰り返す方式とし、会話ごとの取り込み版や処理済みフラグは追加しない。

### DB 単体でコンバートできる範囲

既存の正規化済みデータを新しい列・テーブルへ移す部分変換は設計上可能。ただし、取り込み時に失われた情報は schema migration だけでは復元できず、v0.14.0 に必要なデータが揃う完全変換にはならない。

| 情報 | 既存 DB から移せる範囲と限界 |
| --- | --- |
| 保存済みの会話・本文 | source、session ID、project、title、本文、role、保存済み日時などは移せる。新しい identity への対応は保存形式の確定後に設計する |
| 入力の所属 | 旧 schema に入力 ID はなく、`import_state` と会話を結ぶ外部キーもない。Codex では残存ログの絶対 path と物理行番号から旧 message UUID を再計算して、保存行との対応を直接照合できる。path のルートへの包含や同名 session ID だけでは旧会話の所属を証明しない。対応が不明・競合する旧行は未知として残す |
| Codex の直接親 | 旧取り込みが親 ID を破棄しているため、DB 単体では復元できない。元ログの再読み取りが必要 |
| Claude Code の子・孫 | 未走査の子ログの本文は DB に存在しない。保存済みの `parent_uuid` は発言間リンクであり、会話の直接親を一般に復元する根拠にはならない |
| Codex の発言日時 | 保存値は移せるが、元レコードの時刻か開始時刻による補完かを示す情報はない。元ログなしでは正しい未知日時へ戻せない |
| 元の物理順・本文の構造 | 保存済み行の挿入順は利用できるが、未保存行を含む元 JSONL の厳密な順序や結合前の text block は一般に復元できない。Codex / Cursor の message UUID は path と物理行の hash で、message 行に元 path・行番号を明示的に保持していない |
| 差分取り込み状態 | `import_state` はファイルの path と offset を持つが、新しく読む親子 metadata や未走査の子本文を補うものではない。新規 DB では先頭から読み直す |

根拠は [現行 schema](../internal/core/db_schema.go)、[Codex parser](../internal/ingest/codex/jsonl.go)、[Claude Code の走査](../internal/ingest/claudecode/adapter.go)、[Cursor Agent parser](../internal/ingest/cursoragent/jsonl.go) を参照する。

### Codex の残存ログだけを再取り込みする

1. 旧 DB の保存済み本文・メタデータを新 schema へ限定変換する。元ログのない会話も新しい REF で参照できるようにする。旧行の入力所属は根拠がある場合だけ対応付け、不明なら未知として残す。根拠と保存形式は [確定契約](../docs/specs/v0.14.0-contract.md) を参照する。
2. 残存 rollout の本人の identity と、親から引き継いだ metadata・本文の境界を読み、入力と本人の session ID の組で置換対象を特定する。子ファイル内の親 metadata を別の置換対象や本人の identity 変更とみなさない。ファイル名・入力を無視した ID だけで対象を決めない。同じ入力内で本人の session ID が一致する rollout が複数ある場合は一組として扱う。
3. 対象の旧会話・発言を削除し、対応する元ログを先頭から読み直す。新しい親 ID・原文・日時・順序と、対応する `import_state` の更新を同じトランザクションで保存する。
4. セッション単位で再取り込みに成功した場合だけ置換を確定する。失敗した対象と元ログのないセッションの旧本文は残す。

通常の追記 import だけでは置換にならない。現行の `INSERT OR IGNORE` は同じ UUID の旧内容を更新せず、path が変わると UUID も変わって重複し得る。また、差分取り込みの offset が残ると既存部分を読み直せないため、置換対象の取り込み状態も更新する（[取り込み制御](../internal/core/import.go)、[書き込み処理](../internal/core/db_write.go)）。

現行 import は未解析行をスキップして保存を確定する場合がある。未解析行・読み取りや保存の失敗時に置換を確定してよい条件は、[確定契約](../docs/specs/v0.14.0-contract.md) を参照する（[ファイル処理](../internal/ingest/process.go)）。旧行削除と新しい全文の保存は同じトランザクションで行い、失敗時は対象の旧会話・発言・取り込み状態を残す。再実行時は成功済みの ID も含めて置換し直すため、本文の差分比較や会話単位の再開管理は不要。

ログがない旧 Codex 会話自身の親 ID は未知のまま保持する。新しく取り込んだ子の明示的な親 ID が同じ入力のその旧会話を指す場合は接続できるようにし、入力所属が不明な旧会話や別入力の同名 ID を文面や近い時刻から結びつけない。保存済み時刻の由来や本文構造も推測で補わず、新規取り込みと同じ情報があるとは扱わない。

### 切り替えと現行 CLI の限界

旧 DB を保管した別 DB で、置換された会話、ログがない会話、他 source の本文と参照を確認してから切り替える。再取り込みした範囲では発言番号・REF・取り込み日時が旧 DB と一致するとは限らないため、新しい契約で検証する。

現 CLI にも `--db` で保存先を指定する入口はあるが、セッション単位の置換機能はない。現行の `import --full` は、`--source` を絞っても `messages`・`sessions`・`import_state` を全 source 分削除してから取り込むため、この部分置換には使わない（[取り込み制御](../internal/core/import.go)、[削除処理](../internal/core/db_write.go)）。

共通保存モデルと新しい Codex adapter が動いた後、保存済みデータの限定変換と Codex の部分置換を一つの実装コミットにまとめる。旧 CLI や旧 schema を使い続ける互換層は追加しない。

### 移行の起動と版管理

旧 DB を入力、新 schema の別 DB を出力する専用 `migrate` コマンドを設ける。旧 DB と移行先の指定方法は [確定契約](../docs/specs/v0.14.0-contract.md) を参照する。通常の `import` は差分取り込みのままとし、移行専用の初回コピーや自動置換を担わせない。`search` / `show` は非対応 DB を検出したら移行を案内し、元ログの走査や会話の置換を暗黙に開始しない。

現行にはアプリが管理する DB の版番号はなく、[OpenDB](../internal/core/db.go) と [schema 管理](../internal/core/db_schema.go) が列の有無を調べる。`sessions.version` は元エージェントの版であり、DB の版には使わない。

DB の形式には、アプリ用の整数 revision を [SQLite の `PRAGMA user_version`](https://www.sqlite.org/pragma.html#pragma_user_version) に記録する。アプリの SemVer とは別に管理する。この版は対応する schema の判定だけに使い、初回コピーやログの再取り込みの完了を意味するものにはしない。通常作成した新 schema DB も、別の旧 DB から移行した DB も同じ revision を持ち得るため、revision だけで再実行先を認めない。

版未設定の旧 DB はテーブル・列の形状から、今回移せる既知の形式かを確認する。未知の形式や、実行中のアプリより新しい DB は移行対象にしない。単に整数が対象版以下という理由で、どの旧 DB も同じ処理へ通すことは避ける。

初回は、新 schema の作成・旧 DB の保存済みデータの限定コピー・schema revision・移行元 DB の識別情報・初回コピー完了の記録を一つのトランザクションで確定する。移行元の識別方法は [確定契約](../docs/specs/v0.14.0-contract.md) を参照する。続いて残存ログを走査し、Codex セッションの ID ごとに既存行を削除して全文を保存する。

途中で止まったら、同じ移行先に `migrate` を再実行する。移行先に記録した移行元の識別と初回コピー完了を確認できた場合だけ旧 DB のコピーを省き、現在残っているログの全 ID をもう一度置換する。通常の新規 DB、別の移行元から作った DB、初回コピー完了を証明できない既存 DB は再実行先として拒否する。初回コピー中の中断はそのトランザクションを戻し、新しい移行先への初回実行としてやり直す。成功済みの会話も置換し直してよく、途中の会話位置や会話ごとの完了フラグを保存する必要はない。

元ログがない会話は触らずに残す。後からログが見つかった場合も同じ置換処理を再実行すればよい。専用 backfill や、任意の古い版からの汎用移行機構は設けない。

専用 backfill と旧 DB 向け移行は現行では廃止済み（[ADR 0019](../docs/decisions/0019-remove-legacy-backfill.md)）。今回の履歴保持要件による専用 `migrate` の採用は、実装時にその方針を見直して正本と新しい判断記録へ反映する。

### 実装時に確認する境界

- 新しく取り込んだ会話と旧保存値だけの会話が混在する。旧会話の親不明を「独立した root と確定」と同一視せず、日時の由来・原文の構造も復元できたと扱わない。
- 複数入力に同じ Codex session ID があっても置換対象を混同しない。旧行の入力所属が分からなければ推測で置換せず、元の本文を残す。
- 初回コピーの中断と再実行、通常の新規 DB と別の移行元から作った DB の拒否を確認する。schema revision が一致するだけでは再実行先と判定しない。
- 一つの ID の旧行削除・全文保存が途中失敗で半端に確定しないこと、同じ処理の再実行で重複しないことを確認する。

## 新しい出力

### 入口の分担

| 入口 | 返すもの |
| --- | --- |
| `search [PATTERN]` | 親と関係が分かる子・孫を1行にまとめたセッション一覧。本文抜粋は混ぜない |
| `search --session REF PATTERN` | 指定したまとまり内の全一致箇所と前後の原文 |
| `show REF...` | 選んだ会話の原文。必要な発言範囲・日付・子孫を指定して取得する |

`REF` の具体的な形式は取り込みの identity と一緒に確定する。長さには指定を置かず、コピーして再利用でき、入力・source・子を一意に参照できることを優先する。root だけでなく子だけにも戻れ、入力や source が違う同名 ID、Claude Code の同一 session ID を持つ子を曖昧に解決しない。子の REF を `search --session` に渡したときの探索範囲は担当エージェントが実装契約で選び、理由と利用例を残して、第 7 段階でユーザーに確認する。

### パターンと全一致

- 通常は正規表現、複数 `-e` は OR、`-F` は文字どおりの検索とする。
- まとまり全体で各パターンを満たす AND は専用指定（仮 `--all`）とする。親の `foo` と子の `bar` でも同じまとまりとして成立する。
- 対応構文、大小文字、Unicode、無効式、空一致、位置の単位、同一発言内の重複規則を確定する。rg 完全互換は無条件に約束しない。
- 一覧の一致判定と詳細の一致箇所抽出は同じ照合器を使う。

`search --session REF` はパターン必須。契約化した探索範囲内の関係が分かる会話を検索し、10箇所なら10箇所を返す。実際に一致した会話の REF・発言番号・同一発言内の箇所番号・前後の原文を示す。制限を指定しなければ全件、明示した場合だけ箇所単位で分割する。AND 指定時の詳細にどの一致を載せるかも確定する。

### 一覧の絞り込みと日時

語の省略、project と alias、入力 path、source、期間、dayBoundary、活動日時と区別した `--imported-since` を扱う。入力条件は照合・集約・総数・ページ化より前に適用する。

| 日付条件 | 選択と本文照合 |
| --- | --- |
| `active` | 期間内の原文発言で語を判定する |
| `started` | まとまりの開始日時で選び、本文全体を探す |
| `last` | まとまりの最後の記録日時で選び、本文全体を探す |
| `overlap` | 開始から最後の記録までの区間が指定期間と重なるまとまりを選び、本文全体を探す。開始・最後の記録が期間内の場合だけでなく、指定期間をまたぐ会話も含む。期間内の実発言は必須ではない |

日付だけの `--until` は指定日全体を含み、日時指定の `--until` は排他とする。日時が不明な発言は期間条件に一致させず、条件なしでは失わない。親子で project・日時の有無が異なる場合のまとまり選択、`active` と AND の組み合わせ、並び順と同値時の順序、`--imported-since` のまとまりへの適用は仕様化する。

### 集約、総数、ページ化

候補条件で絞る → 本文を照合する → 親子のまとまりに集約する → 総数を数える → 並べる → ページ化する。件数制限後に正規表現を掛けない。

modernc SQLite v1.29.0 の deterministic scalar function に bind した pattern と本文を渡し、Go の照合器で候補を絞れることを `:memory:` DB の実験で確認した。既存の [関数登録](../internal/core/db.go) と同じ経路を使える。SQL の真偽判定と詳細の一致位置抽出で同じ照合器を使う。これは接続と照合の成立確認であり、全量検索の性能確認ではない。任意の正規表現では候補本文の全走査が起こり得るため、一覧実装時に実データで時間を測る。

TSV・JSON で全 filter 後・ページ化前の `total`、今回の件数、`--limit` / `--offset`、続きの有無と次位置を返す。一覧の `total` はまとまり数、詳細の `total` は一致箇所数。0件・末尾超過でも総数を返し、一度の検索内で件数と項目を一致させる。列・JSON field・総数の置き方・既定の limit は契約確定時に明示する。

### 原文取得

本人の全文を既定にする。子だけの REF、親と子孫をそれぞれ別の本文として含める指定、複数 REF の一括取得、JSON 出力を提供する。会話を選んだ後の表示を、発言のフィルタと `limit` / `offset` による表示範囲の選択にまとめる。role・発言番号範囲・指定日の実発言で絞り、元の順序で並べた後にページ化する。番号はフィルタやページ化後に振り直さない。role フィルタ・limit / offset・一行表示は独立して組み合わせられるオプションとする。一行表示は、選ばれた各発言の本文の最初の行だけを表示する。改行を除いて全文を連結する処理ではなく、二行目以降は表示しない。フィルタとページ化は短縮前の原文に対して適用し、一行への短縮は最後に行う。先頭・末尾の取得方法、複数会話時のページ化単位、具体的なフラグは契約確定時に詰める。

発言番号は検索の詳細と `show` で一致させる。指定日の取得では、セッション開始日だけで選ばず、その日の実発言を返す。複数 REF や子孫指定が重なった場合の重複・順序を決める。元ログに根拠のない文脈除外や時刻補完はしない。

独立した `sessions` は `search` の一覧へ統合する。期間だけで複数全文を出す入口は、一覧で REF を選び `show REF...` に渡す形へ移す。一括取得能力は維持する。agent が一度のシェル呼び出しで検索 JSON から必要な REF を選択・重複排除して `show REF...` に渡せる例を usage・README・skill に置く。追加の一括専用コマンドは設けない。既存の `outline`・`--summary`・`--turn` は独立した入口としての互換性維持を求めず、`show` の発言フィルタ・表示範囲へ統合する。`outline` の用途は各発言の最初の一行だけを表示する独立オプションに移し、role フィルタ・表示範囲と自由に組み合わせる。`--tail` と表示除外設定もこの原文取得の契約で整理し、無関係な機能整理へ広げない。

## コミットの進め方

各実装タスクは、動く保存・取得経路、対応する fixture / 回帰検証、必要な正本・usage・README 両言語・skill の更新を含むコミット単位とする。使われない schema だけを先行させず、取り込みと保存をつなぐ。検証と文書同期を最後だけに残さない。

複数入力からの保存・取得を先に動かし、その入力で区切った同じ REF とまとまり解決を原文取得・検索の両方で使う。入力テーブルの短い ID を参照して path の反復保存を避け、一覧・検索の実データ測定で十分な性能か確認する。最後は「単語から過去作業へ戻る」「指定日の実発言を Daily Note へ渡す」の二つの経路を複数入力でも通して確認する。詳細の必須 gate は [検証ルール](../docs/rules/verification.md) を参照する。
